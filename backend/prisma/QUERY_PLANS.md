# Плани запитів: журнал оцінок і leaderboard

Перевірка з ТЗ, тиждень 6, п. 6.1: `EXPLAIN` для журналу оцінок і таблиці лідерів, індекси — за потреби.

**Підсумок:** нових індексів не додавали, бо наявних достатньо. Журнал гальмував через **форму запиту**: фільтр по зв'язку `lesson.groupId` Prisma перетворює на JOIN, і Postgres обирав послідовне сканування всієї таблиці `grades`. Запит переписано (`gradeService.getGrades`/`getSummary`): журнал групи прискорився з ~30 до ~5.5 мс, зведення — з ~33 до ~1.4 мс, обидва тепер іде через наявний індекс `grades(lesson_id)`. Leaderboard уже працює через індекси або на незначному обсязі; поріг, з якого знадобиться індекс, описано нижче.

## Методика

- Локальний PostgreSQL 16 з **дефолтними** налаштуваннями планувальника (`random_page_cost = 4`). Схема створена з `migrations/0_init`, тобто ідентична продовій.
- Обсяг — «академія через кілька років роботи»:

  | Таблиця | Рядків |
  |---|---|
  | `grades` | 208 218 |
  | `attendance` | 160 200 |
  | `coin_transactions` | 99 000 |
  | `lessons` | 6 000 (60 груп × 100 занять) |
  | `users` | 1 863 (1 800 студентів по 30 у групі, 60 викладачів) |

- SQL ніхто не писав вручну. Скрипт викликав **справжні сервіси** (`gradeService`, `coinService`, `userService`, `lessonService`) від імені адміна, викладача й студента. Плани кожного запиту, який згенерувала Prisma, збирав `auto_explain` (`log_analyze`, `log_buffers`). Час нижче взято з другого прогону, на прогрітому кеші.

## Журнал оцінок (`GradesPage`)

Сторінка робить чотири запити: студенти групи, заняття групи, оцінки групи за типом, зведення середніх. Перші два одразу йдуть через індекси `users(group_id)` і `lessons(group_id, date)` і займають менше 0.4 мс. Проблема була в двох останніх.

### Було

```sql
SELECT grades.* FROM grades
LEFT JOIN lessons j0 ON j0.id = grades.lesson_id
WHERE grades.type = 'classwork' AND j0.group_id = $group ...
```

```
Gather Merge  (actual time=24.368..26.617 rows=2100)
  Buffers: shared hit=10740
  ->  Hash Join  (Hash Cond: grades.lesson_id = j0.id)
        ->  Parallel Seq Scan on grades  (rows=42687 loops=3)      ← уся таблиця
              Filter: (type = 'classwork')
        ->  Bitmap Index Scan on lessons_group_id_date_idx (rows=100)
```

Щоб показати 2 100 оцінок однієї групи, Postgres прочитав усі 128 тисяч оцінок типу `classwork` в академії. Вартість такого запиту росте разом з **усією** таблицею `grades`, а не з розміром групи.

### Чому саме так

Альтернатива — пройти 100 занять групи і для кожного взяти оцінки з індексу `grades(lesson_id)`. За дефолтного `random_page_cost = 4` планувальник оцінює цей шлях у ~7 400 одиниць проти ~5 100 у паралельного seq scan і обирає другий. Перевірки:

| Варіант | Час |
|---|---|
| Як було (JOIN, індекс `grades(lesson_id)`) | 29 мс |
| JOIN + новий індекс `grades(lesson_id, type)` | 29 мс, планувальник так само обирає seq scan |
| JOIN + `SET random_page_cost = 1.1` (типове значення для SSD) | 5 мс і зі старим, і з новим індексом |
| **`lesson_id IN (...)` + старий індекс, дефолтні налаштування** | **4.4 мс** |

Отже, додатковий індекс нічого не дає. Вирішальні дві речі: форма запиту та налаштування вартості.

### Стало

Сервіс спершу бере id занять групи (`lessonRepository.findIdsByGroup`, ~0.3 мс по індексу), а потім фільтрує оцінки по `lessonId IN (...)`:

```
Sort  (actual time=3.823..3.909 rows=2100)
  Buffers: shared hit=465
  ->  Bitmap Heap Scan on grades  (rows=2100)
        ->  Bitmap Index Scan on grades_lesson_id_idx  (rows=3445)
```

Для викладача, який відкрив журнал **своєї** групи, прибрано також умову `OR (teacherId = я OR lesson.groupId IN мої групи)`. У такому разі вона нічого не звужує: усі оцінки власної групи викладачу видно й так. Натомість додавала ще один JOIN на всю таблицю `lessons`. У чужій групі умова лишилася, і викладач, як і раніше, бачить там лише виставлені ним оцінки. Обидва випадки покриті тестами в `grade.service.test.ts`.

| Запит | Було | Стало | Буфери |
|---|---|---|---|
| Оцінки групи, викладач | 28.1 мс | 5.4 мс | 10 740 → 465 |
| Оцінки групи, адмін | 31.1 мс | 5.6 мс | 4 438 → 465 |
| Зведення середніх (`/grades/summary`) | 33.4 мс | 1.4 мс (+0.3 мс id занять) | 3 990 → 349 |
| Оцінки студента (`studentId`) | 1.1 мс | 1.2 мс | без змін, `grades(student_id)` |

## Leaderboard (`CoinsPage`, `DashboardPage`)

| Запит | План | Час |
|---|---|---|
| Рейтинг групи (викладач, студент) | Bitmap Index Scan `users_group_id_idx` → top-N по 30 рядках | 0.04 мс |
| Загальний рейтинг (дашборд адміна/викладача) | Seq Scan `users` (1.8k) → top-N heapsort | 0.8 мс |

Рейтинг читає вже матеріалізований `User.redCoins`, а не агрегує транзакції (див. `coin.repository.ts`), тому він дешевий. Для загального рейтингу окремо перевірено запас, додавши 18 000 студентів у транзакції з подальшим відкатом:

| Студентів | Без індексу | З `(role, is_active, red_coins DESC, last_name)` |
|---|---|---|
| 1 800 | 0.8 мс | — |
| 19 800 | 6.9 мс | 0.08 мс |

**Рішення — поки без індексу.** `red_coins` змінюється при кожному нарахуванні монет. Індекс на цій колонці вимикає HOT-оновлення: кожне нарахування почне оновлювати й усі індекси `users`. Виграш з'явиться лише на десятках тисяч студентів. Коли загальний рейтинг почне займати понад ~5 мс, досить додати в `User`:

```prisma
@@index([role, isActive, redCoins(sort: Desc), lastName])
```

і згенерувати міграцію: `npm run prisma:migrate -w backend -- --name leaderboard_index`.

## Помічено попутно (не в межах цієї задачі)

- ~~**`GET /coins/transactions` без пагінації.**~~ Виправлено, див. розділ «Історія RedCoins» нижче.
- **FK без індексів**: `grades.teacher_id`, `lessons.teacher_id`, `coin_transactions.issued_by`, `coin_transactions.related_lesson_id`. Зараз вони не на гарячих шляхах: користувачів і заняття не видаляють фізично, а деактивують/скасовують. Якщо з'явиться справжнє видалення, без цих індексів кожне `DELETE` скануватиме дочірні таблиці.
- **`ORDER BY lesson.date` у журналі** будує хеш по всій таблиці `lessons` (~1.4 мс на 6 000 занять). Поки дешево, але це наступне місце, яке ростиме з історією.
- **`random_page_cost` на Neon.** Дефолт Postgres — 4, розрахований на HDD. Значення на своєму проєкті можна перевірити через `SHOW random_page_cost;`. Для SSD зазвичай ставлять `1.1` (`ALTER DATABASE neondb SET random_page_cost = 1.1;`), тоді планувальник охочіше обирає індекси. Журнал від цього більше не залежить, тож це опційне налаштування, а не вимога.

## Історія RedCoins (`GET /coins/transactions`)

Раніше ендпоінт віддавав усю вибірку одним запитом. Адмін отримував увесь ledger (99 000 рядків на тестовому обсязі), а `CoinsPage` фільтрувала його за групою **на клієнті**. Тепер це keyset-пагінація: `?limit=` (20 за замовчуванням, максимум 100) і `?cursor=` (id останньої транзакції попередньої сторінки). Відповідь має форму `{ items, nextCursor }`. Фільтр групи (`?groupId=`) тепер застосовує сервер.

### Курсор: власна умова замість Prisma `cursor`

Prisma `cursor: { id }` генерує таку умову:

```sql
WHERE (created_at = X AND id <= Y) OR created_at < X
```

Через `OR` Postgres не може почати скан індексу з позиції курсора: на глибоких сторінках він перечитує всі новіші рядки, як при `OFFSET`. Тому `coinRepository.findPage` будує умову сам:

```sql
WHERE created_at <= X AND (created_at < X OR id < Y)
ORDER BY created_at DESC, id DESC
LIMIT limit + 1
```

Перша частина (`created_at <= X`) стає умовою індексу (`Index Cond`). Зайвий (`limit + 1`)-й рядок показує, чи є наступна сторінка, без окремого `COUNT`. Прохід усією історією групи (1 650 транзакцій) сторінками по 100 дав 17 сторінок: усі транзакції унікальні, без дублів і пропусків.

### Фільтр групи: через id студентів

Як і з оцінками, зв'язок `student: { groupId }` Prisma перетворює на JOIN. Тому сервіс спершу бере id студентів групи (`userRepository.findStudentIdsByGroups`), а потім фільтрує `studentId IN (...)` по наявному індексу `coin_transactions(student_id, created_at)`:

| Запит (20 рядків на сторінку) | Було: усе одним запитом | Стало |
|---|---|---|
| Група (UI адміна/викладача), 1-ша сторінка | ~15 мс + уся академія на клієнт | 1.1 мс |
| Та сама група, сторінка після 1 000 рядків | — | 0.5–1.2 мс |
| Викладач, усі свої групи (2) | ~20 мс, Seq Scan | 1.2–2.1 мс |
| Студент, власна історія | ~0.1 мс | 0.06–0.14 мс |
| Адмін без фільтра (UI цього не робить) | 99 000 рядків | 12–28 мс, Seq Scan, але 21 рядок у відповіді |

### Індекс для «всієї академії» — не додано

Перевірено два кандидати:

| Індекс | Адмін, уся академія | Група (запит UI) | Порожня група (0 транзакцій) |
|---|---|---|---|
| без нового (як зараз) | 12–15 мс | **0.7 мс** | **0.2 мс** |
| `(academy_id, created_at DESC)` | 12–15 мс — не використовується: запит не фільтрує за `academy_id`, тож індекс не дає порядку сортування | без змін | без змін |
| `(created_at, id)` | **0.2 мс**, глибока сторінка 0.85 мс | 3.5 мс (через JOIN — 7 мс) | **42 мс** (через JOIN — 93 мс) |

`(created_at, id)` пришвидшує запит, якого UI не робить: для персоналу `CoinsPage` завжди передає групу. Натомість він шкодить запиту, який UI робить. Планувальник починає йти індексом «назад від найновіших» і фільтрувати студентів групи. Для групи, у студентів якої мало транзакцій, це означає прочитати майже весь ledger. Тому індекс не додаємо. Якщо з'явиться екран «уся історія академії», варто повернутися до `(created_at, id)` і перевірити, що запити групи й далі йдуть по `(student_id, created_at)`.
